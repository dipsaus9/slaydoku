## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Outcome: once every suspect is placed, the remaining board cell is placed by the player's own tap, not auto-written; the victim stays out of hints and out of the normal suspect pick list.
Type: deliverable
Branch: SLAY-9.24/victim-manual-final-placement

Context: SLAY-9.5 made the victim auto-fill the one remaining square the instant every suspect is placed, and removed the victim card's tap-to-select wiring (SuspectPanel.tsx / CardGrid.tsx / VictimCard.tsx), since at the time the victim was wrongly manually placeable and hintable. The owner now wants the auto-fill part reverted: the player should make that last placement themselves, as the satisfying final move of the puzzle. The victim must stay excluded from hints (hints.ts's suspects-only filtering, untouched) and stay out of the normal pick list (the victim card itself must not become a new way to select/place them at any earlier point) -- only the natural last board tap places them.

Mechanism already mostly in place: PlayScreen.tsx's order array lists suspects then the victim, and afterPlace's nextUnplaced already auto-advances selectedId to the victim's id the moment the last suspect lands, well before this story. The reducer's generic place() action already accepts any person id, victim included (SLAY-9.5's own notes confirm manual placement was left enabled at the reducer level). So the actual change is narrower than it looks: stop the reducer from writing the victim's placement automatically, and give the player a visible cue that it is now their move.

Post-merge bug fix (found by a fresh coordinator review of PR #98 before merge, reproduced on CI and locally): this branch's own SLAY-9.24 delivery correctly removed reducer.ts's auto-fill of the victim, but missed that src/validation/walk.ts's walkHints() -- which simulates a player who follows every level-3 hint to the end -- relied on that same auto-fill as a silent side effect to reach 'solved'. The victim is deliberately never a hint subject (hints.ts's nextStep never suggests placing them, unchanged since SLAY-9.5), so once auto-fill was removed, walkHints() placed every suspect via hints, asked for the next hint, got null, and broke out of its loop with the victim still unplaced -- returning {solved:false, unplaced:1} for essentially every puzzle. This is load-bearing: auditHints() (src/validation/hints.ts) calls walkHints() directly and flags any unplaced!==0 walk as a problem; that audit is wired into content/packs/gates.ts's entryProblems, the schedule generator, and the ladder generator's own tests. Confirmed root cause directly: before the fix, hardPuzzle() (src/game/hints.fixture.ts) threw 'no hard 6x6 puzzle with a note as its first hint in 100 seeds' because buildEntry's gate rejected every single seed on this exact walk failure; src/engine/generator/ladder/generate.test.ts's 'pins the gift on every gift cell' tests failed the same way (matches the bug report's own repro exactly). This was NOT the CPU-contention issue the original delivery's notes attributed 20 failing files to -- that diagnosis was wrong; the real cause was this functional gap. Fix: walkHints() now does, after its main while-loop (not inside it, so it runs at most once, after hints are truly exhausted): if not yet solved and the victim is unplaced while every suspect is placed, derive the victim's cell with deriveVictimCell (src/engine/model/rules.ts, still exported, only its automatic wiring into the reducer was removed by this story) and apply an ordinary reduce(puzzle, state, {type:'place', personId: victim.id, cell}) -- exactly the cell/logic board.ts's old withAutoVictim used, just invoked explicitly and once, and NOT recorded as a WalkStep (no hint fires for it, so it must not look like one to auditHints()'s per-step checks). Also checked src/game/hints.fixture.ts's hintPath(): its purpose is collecting hint texts for pinning/review, not asserting completion, and no test reads a final solved-state off it directly, so it needed no equivalent change -- confirmed by reading every hintPath() call site in hints.test.ts. However, 4 tests in src/game/hints.test.ts run their OWN raw hint-follow loops directly (not via walkHints or hintPath) and asserted the final state was 'solved': these had the identical gap and were failing (confirmed by running the file before this fix: 4 failures, 'expected playing to be solved'). Added a small finishVictim(puzzle, state) test helper (same pattern: look up the victim's true cell from puzzle.solution once every suspect is right, place them explicitly) and used it in those 4 tests. Added an explicit new test case per the coordinator's request: src/validation/walk.test.ts now asserts the demo puzzle's walk never gives the victim a WalkStep (no placement or focus names them) yet still ends solved with unplaced:0.
